# ProofOfWork development instructions

ProofOfWork is a Devnet hackathon prototype for structured student internships and verified work experience. Use fictional organizations and internships and clearly labeled non-monetary DEMO tokens. Keep personal data, private work evidence, and credentials off-chain. Describe verification as an authorized attestation of agreed conditions, and report implemented and proposed capabilities accurately.

- Use Solana Devnet exclusively for RPCs, transactions, deployments, and Explorer links. Use no Mainnet, real stipends, or customer funds. Obtain explicit approval before deploying or generating a program or deployment keypair.
- Ask Harshita or Palak for required program IDs, public addresses, mints, RPC endpoints, and other external configuration. Never invent them. Document non-secret placeholders only where needed. Configure credentials locally through environment variables or approved secret storage. Never ask for secrets in chat or expose them in frontend code, logs, or commits. Never commit private keys, seed phrases, wallet files, or local .env files.
- Develop on assigned feature branches and integrate through reviewed pull requests. Never push directly to main or commit, push, merge, rebase, or reset without explicit instruction. Never force-push. Keep changes focused and preserve tested functionality. Explain and obtain approval for changes that affect previously working features.
- Follow the ownership in [Team workflow](docs/TEAM_WORKFLOW.md). Palak and Harshita use separate branches and jointly approve account layouts, PDA seeds, instruction signatures, state transitions, and other shared Rust definitions before changes. Obtain approval before touching another developer's assigned modules.
- Enforce authorization and financial invariants in the program. Validate signers, PDA relationships, account ownership, token program and mint, vault and recipient authorities, state transitions, checked arithmetic, refund eligibility, and duplicate or replayed operations. The frontend is not a security boundary.
- Keep the architecture minimal. Reuse the approved Anchor and Solana stack and avoid unrelated Web3 SDKs, unnecessary abstractions, or speculative features.
- Run relevant tests and existing regressions before committing. New blockchain functionality requires negative tests for authorization, account constraints, financial invariants, and invalid transitions. Only report checks that actually passed. Report limitations and avoid deployment or transaction tests without permission.
- Before committing, report changed files and verification results. When finished, report the scope, preservation of existing functionality, unresolved issues, current branch, and working-tree status.
